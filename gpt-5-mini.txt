**5. New System Design (Greenfield Replacement)**

High-level goals:
- Strongly consistent appointment creation with idempotency.
- Reliable delivery of notifications via transactional outbox.
- Resilient external calls using retries + exponential backoff, circuit breaker, timeouts.
- Observable: structured logs with request_id and metrics for retries, durations, and success rates.
- Clear service decomposition: API gateway, Appointment Service, Router/Compute Service (stateless), Outbox Sender Worker, DB (Postgres), Message broker optional (Kafka) for scale.

Capability boundaries / service decomposition:
- API Gateway / Auth (ingress) — validation, rate limiting, auth.
- Appointment Service (stateless): exposes appointment API, idempotency handling, writes to DB + outbox.
- Routing Service (stateless): computes availability and route using graph; invoked by Appointment Service.
- Outbox Sender (worker): reads DB outbox, sends to downstream, updates outbox state, publishes events to event bus.
- Audit & Reconciliation Service: periodic checks for pending/outstanding transactions and triggers compensations.
- Observability: centralized logs (structured), traces (OpenTelemetry), metrics (Prometheus).

Unified state machine (appointment lifecycle):
- init -> validated -> computing -> scheduled -> notified -> completed
- failure transitions: validated -> failed, computing -> revert /failed, scheduled -> pending_notification -> notified or notification_failed -> retry/compensate -> cancelled/failed

Idempotency & retries:
- Require client `Idempotency-Key` header or generate server token and return it.
- Store idempotency key -> appointment_id mapping with unique constraint.
- Retry sender uses exponential backoff with jitter. Retries are handled by outbox worker reading unsent messages.
- Short synchronous retries for transient errors (e.g., network), but never create duplicates due to idempotency.

Timeout and circuit-breaker:
- All outbound HTTP calls use a per-call timeout (e.g., 2s).
- Circuit breaker wraps repeated failures to fail fast (CB state persisted in-memory or in Redis for multi-instance).
- Use circuit breaker with gradual reset and monitoring.

Compensation / Saga:
- For multi-resource flows (if external systems must be updated), prefer Saga with compensating steps (e.g., if calendar update fails after DB update, create compensation job to cancel appointment).
- If all operations are local DB + outbound notifications, transactional outbox suffices.

Architecture diagram (ASCII):
API Gateway -> Appointment Service -> (Routing Service)
                                 |
                                 v
                              Postgres (appointments + outbox)
                                 |
                                 v
                            Outbox Sender -> Downstream APIs
                                 |
                                 v
                            Event Bus / Audit

Key interfaces and sample schemas (JSON):

- Create Appointment request (API):
{
  "user_id": "string (uuid)",
  "start_time": "ISO8601",
  "duration_minutes": "int >= 1",
  "location": "string",
  "metadata": { "notes": "string" }
}

Field constraints:
- user_id: required, uuid
- start_time: required, ISO8601 UTC
- duration_minutes: required, int between 1 and 1440
- location: optional, max 256 chars
- metadata: optional object, limit 4kb

Response:
{
  "appointment_id": "uuid",
  "status": "scheduled|pending_notification|failed",
  "idempotency_key": "string"
}

Outbox message schema:
{
  "id": "uuid",
  "appt_id": "uuid",
  "type": "notification.create",
  "payload": { ... },
  "attempts": 0,
  "next_attempt_at": epoch_seconds,
  "status": "pending|sent|failed"
}

Validation:
- Enforce JSON schema validation at API gateway and again in service.
- Use strong input validation to avoid downstream errors.

Migration & parallel run strategy
- Approaches:
  1) Dual-write + Backfill (safe, more complex):
     - Run new service in parallel.
     - For incoming traffic, run shadow writes to new DB or message bus.
     - Backfill historical data into new DB.
     - Gradually cutover reads by using new service for new requests, but keep legacy reads for old records until backfill completes.
  2) Read-through / Feature flag cutover:
     - New service receives writes; legacy still reads for read-only endpoints.
     - Switch read traffic slowly.
  3) Blue/Green with event-driven sync:
     - Use event bus to replicate writes from old system into new system.
- Recommended steps (dual-write approach):
  - Step 0: Prepare DB schema and outbox table; add unique constraints for idempotency keys.
  - Step 1: Deploy outbox sender and routing service in test env; run smoke tests.
  - Step 2: Enable shadow write in API layer: primary write to legacy, *also* write to new DB/outbox.
  - Step 3: Backfill historic appointments into new DB using one-off migration jobs, ensuring idempotency keys are set.
  - Step 4: Run reconciliation: compare legacy vs new for sample set; fix divergences.
  - Step 5: Cutover reads to new system for a small percent of traffic; monitor.
  - Step 6: Gradual 100% cutover; keep legacy in read-only mode for a period then deprecate.

Rollback paths:
- Keep legacy read/write path intact until new system demonstrates parity.
- On major errors, revert API gateway behavior to stop dual-write to new system.
- Replay outbox messages or backfill missed messages.
