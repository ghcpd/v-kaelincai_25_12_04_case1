## 5) Greenfield replacement — target system design (appointment scenario)
Goal: Replace a brittle, tightly coupled flow with a resilient, observable, maintainable appointment service that supports strong idempotency, retries with exponential backoff, circuit-breaker behavior for external providers, compensation with transactional outbox, and clear audit logs.

High-level capability boundaries (microservices or modules):
- API Gateway / Request-ingress (HTTP)
- Appointment Orchestrator (statemachine for appointment lifecycle)
- Persistent Storage (appointments table + outbox)
- Calendar Adapter (external provider client + circuit-breaker)
- Background worker (outbox delivery + compensation/reconciliation)
- Observability (structured logs + metrics + events)

Key properties:
- Idempotency: each request carries request_id; operations are idempotent if request_id reused.
- Retry/backoff: exponential backoff with bounded retries for external calendars.
- Timeouts/circuit-breaker: short RPC timeouts + circuit-breaker opening on repeated failures to avoid backend overload.
- Compensation (Saga pattern): if an external step fails permanently, perform compensating actions (e.g., mark appointment failed, send notifications, rewind state).
- Transactional outbox: ensure local DB update and event emission is atomic in practice (simulate via outbox table, processed by worker).
- Observability: each request/appointment carries unique appointment_id and request_id; structured logs; sensitive fields masked.

State machine (simplified):
- INIT → PENDING → SCHEDULED (success) OR FAILED → COMPENSATED/ROLLED_BACK (if step failed and compensation applied)
- Outbox events: appointment.created, appointment.scheduled, appointment.failed, appointment.compensated

Idempotency rules:
- Create with request_id that maps to an appointment — subsequent same request_id returns existing appointment, does not duplicate external calls.
- Retry with backoff must not re-create resources if already succeeded.

Timeout & Circuit Breaker:
- Set low per-call timeout (e.g., 1.5s).
- Circuit breaks after N consecutive failures (e.g., 5) and stays open for 30s.
- On open, calls fail-fast and fallback path or enqueue for reprocessing.

Compensation (Saga) strategy:
- Stages modeled as small compensable steps.
- If calendar scheduling fails after retries, orchestrator either:
  - Retries via outbox worker later, OR
  - Runs compensating action (delete local appointment) and publishes appointment.failed for user-facing logic.

## 6) Architecture & data flow (ASCII diagrams + prose)

Request flow (happy path):
1. Client -> API gateway (POST /appointments, request_id)
2. Orchestrator validates input, checks idempotency store
3. Writes appointment row in DB in state PENDING and writes outbox event appointment.pending (Atomic pair)
4. Calls Calendar Adapter (RPC) with idempotency key
5. On success: mark appointment SCHEDULED, append outbox event appointment.scheduled
6. Outbox worker sends events downstream (notifications)

ASCII diagram:
Client -> API -> Orchestrator (validate, idempotency) -> DB [+ Outbox] -> Calendar Adapter -> DB on success OR failure -> Outbox Worker -> Downstream (Notification)

Schemas (compact):
- Appointment record
  - id: uuid (PK)
  - request_id: string (idempotency key)
  - user_id: string
  - start_time: datetime (ISO8601)
  - end_time: datetime
  - status: ENUM {PENDING, SCHEDULED, FAILED, COMPENSATED}
  - metadata: JSON (masked)
  - created_at, updated_at

- Outbox event
  - id: uuid (PK)
  - appointment_id: uuid
  - event_type: string
  - payload: JSON
  - attempts: int
  - last_attempt_at: timestamp | null
  - acked: bool

Field constraints:
- request_id length <= 256, must be unique when status != failed
- start_time, end_time required; start_time < end_time
- status transitions validated by state machine
